# BioSync API Contracts

Status: BioSync v1 transport contract; implementation notes synchronized on 2026-10-11.

The scientific iAUC calculation policy is defined separately in
[IAUC_POLICY.md](IAUC_POLICY.md).

Source: [PROJECT_SPEC.md](PROJECT_SPEC.md).

Implemented endpoints: `POST /v1/analyses` and `GET /health`. The original
`MealRecord` persistence design and `POST /v1/food-recognition` contract below
are reserved, unimplemented designs, not prerequisites of the current manual
meal workflow. No API fields or schemas were changed by this documentation sync.

## Common conventions

- Client/backend communication uses HTTPS.
- API request and response field names use `snake_case`.
- API timestamps use UTC ISO 8601 with a `Z` suffix, for example `2026-09-11T00:00:00Z`. Fractional seconds are permitted. Timestamps without a timezone are invalid.
- Meal IDs are UUID strings generated by the mobile app.
- Glucose values use mmol/L, explicitly named `value_mmol_l`.
- Numeric fields must contain finite JSON numbers.
- JSON requests use `Content-Type: application/json`. Image uploads use `multipart/form-data`.
- Success responses and application error responses use JSON.
- CV and LLM credentials remain on the backend.
- Public responses contain normalized application data, not raw provider responses.

### Local ownership and stateless processing

The current mobile app owns its draft, food information, selected readings and
result in memory. SQLite, image storage and restart recovery are not implemented.
The original local-persistence design is retained in the reserved MealRecord
section; it is not a current durability guarantee.

The backend does not retain meal state between requests. A `meal_id` correlates a response with a local meal; it does not identify a stored backend resource.

The analysis request contains the manually entered food information and all
glucose readings required for that calculation. It does not depend on a previous
request. Diagnostic-only loads stay on the device; submitting a meal sends the
normalized records, including source IDs, to the configured backend. The LLM
receives only the whitelisted food and derived analysis context, not those IDs
or raw glucose records.

### Error response

Application errors use this envelope:

```json
{
  "error": {
    "code": "UPSTREAM_TIMEOUT",
    "message": "The external service did not respond in time.",
    "retryable": true
  }
}
```

| Field | Type | Meaning |
|---|---|---|
| `error.code` | string | Stable, provider-neutral error identifier. |
| `error.message` | string | Human-readable explanation without credentials or raw provider responses. |
| `error.retryable` | boolean | Whether retrying the unchanged request may succeed after a transient failure. |

Shared transport and integration errors:

| HTTP status | Code | Meaning |
|---|---|---|
| `400` | `INVALID_REQUEST` | Missing fields, invalid field types, invalid timestamps, or malformed request content. |
| `415` | `UNSUPPORTED_MEDIA_TYPE` | Unsupported request or image media type. |
| `502` | `UPSTREAM_FAILURE` | An external service failed or returned a response the backend could not normalize. |
| `504` | `UPSTREAM_TIMEOUT` | An external service did not respond within the backend's request timeout. |
| `500` | `LLM_CONFIGURATION_ERROR` | Backend feedback mode, key, model/access configuration or provider quota requires operator action. Not retryable without a configuration/account change. |
| `502` | `LLM_AUTHENTICATION_ERROR` | Feedback provider rejected backend credentials or access. Not retryable. |
| `502` | `LLM_NETWORK_ERROR` | Backend could not connect to the feedback provider. Retryable. |
| `503` | `LLM_RATE_LIMITED` | Transient feedback-provider rate limit. Retryable later. |
| `502` | `LLM_INVALID_RESPONSE` | Feedback response was malformed, refused, incomplete or failed output validation. Not automatically retryable. |

For dietary feedback, `UPSTREAM_TIMEOUT` and transient `UPSTREAM_FAILURE` are
retryable. These integration errors are separate from glucose-policy errors.
Real-provider mode never silently falls back to mock feedback. The request and
`AnalysisResult` structures remain unchanged. See [LLM_INTEGRATION.md](LLM_INTEGRATION.md)
for backend-only configuration and the provider data boundary.

Scientific data eligibility and calculation-specific rejection rules are defined in [IAUC_POLICY.md](IAUC_POLICY.md).

## 1. MealRecord (reserved persistence/recognition design; not implemented)

A proposed local mobile model. Neither endpoint accepts or returns the entire
`MealRecord`. The current app instead uses transient ViewModel state; the enum,
image field and persistence/restart guarantees below describe the deferred design.

All fields below are present; nullable fields begin as `null`.

| Field | Type | Meaning |
|---|---|---|
| `id` | UUID string | Locally generated meal identifier, sent as `meal_id` in API requests. |
| `meal_at` | UTC ISO 8601 string | User-confirmed meal start; calculation interval is defined in IAUC_POLICY.md. |
| `image_uri` | string | Local URI of the image in persistent app storage. Never sent as an API image reference. |
| `status` | string enum | Current local workflow stage. |
| `food_info` | `FoodInfo` or null | Stored normalized food-recognition result. |
| `analysis_result` | `AnalysisResult` or null | Stored completed analysis for this meal. |
| `last_error` | object or null | Most recent error, using the `code`, `message`, and `retryable` fields defined above. |

Allowed `status` values:

| Value | Meaning |
|---|---|
| `pending_recognition` | The meal and image are saved locally; food recognition has not succeeded. |
| `waiting_glucose` | Food information is saved; the app is waiting for the required monitoring period and readings. |
| `pending_analysis` | Food information and the readings selected under the confirmed policy are saved locally; analysis has not succeeded. |
| `completed` | The completed analysis is saved locally. |

The intended progression is:

```text
pending_recognition → waiting_glucose → pending_analysis → completed
```

A transient failure preserves the current stage and cached data. The app records the error and can retry that stage. App restart must recover the stored stage.

Monitoring deadlines, reading-selection rules, and scientific conditions for advancing to `pending_analysis` are defined in [IAUC_POLICY.md](IAUC_POLICY.md).

This document does not prescribe a SQLite table layout. Nested objects may be persisted separately as long as their associations are preserved.

## 2. GlucoseReading

A normalized glucose measurement held in memory and included in an analysis request.

| Field | Type | Meaning |
|---|---|---|
| `source` | string | Source identifier; current providers use `health_connect` and `samsung_health`. This is a string, not a closed enum. |
| `source_record_id` | string | Required stable record identifier for local association and traceability; see the identifier rules below. |
| `measured_at` | UTC ISO 8601 string | Measurement timestamp. |
| `value_mmol_l` | number | Glucose concentration in mmol/L. |

When the source provides a stable record identifier, use that identifier as `source_record_id`. For imported or test data without a source-provided identifier, the mobile application may generate a stable identifier during import. `source_record_id` remains a required string.

The mobile app normalizes source units before use and upload. Values in another unit must not be placed in `value_mmol_l`.

The analysis request supplies the meal association once through its top-level
`meal_id`. Samsung series samples use stable parent-UID/timestamp-derived IDs;
source package metadata remains diagnostic-only and is not an API field.

Source identifiers do not introduce backend device or user resources.

Required temporal coverage, duplicate-measurement handling, and scientific validity rules are defined in [IAUC_POLICY.md](IAUC_POLICY.md).

## 3. FoodInfo

Provider-neutral food information, currently populated by manual input.

| Field | Type | Meaning |
|---|---|---|
| `recognized_at` | UTC ISO 8601 string | Manual draft confirmation time in the current app; recognition-result time in the reserved CV flow. |
| `items` | array of objects | One or more food items; the current manual form creates one. |

Each item contains:

| Field | Type | Meaning |
|---|---|---|
| `name` | string | Non-empty food label. |
| `weight_g` | number, optional | Approximate manually entered food weight in grams; must be finite and strictly greater than zero when supplied. |
| `confidence` | number, optional | Confidence between 0 and 1, only when the provider supplies a value that can be represented meaningfully in this form. |

Do not invent confidence values when unavailable.

Omit `weight_g` when unknown or left blank; do not send `null`. Numeric strings,
booleans, zero, negative values, NaN and Infinity are invalid. No application
upper bound is imposed. Weight is optional dietary context for the LLM and
must not change the deterministic iAUC calculation. It does not imply nutrient
quantities, calories, serving units, volume, density or food database IDs.

Manual input uses one item, for example `{"name": "Chicken rice", "weight_g": 350}`,
or `{"name": "Chicken rice"}` when weight is unknown. In the manual flow,
`recognized_at` records the user's confirmation time; it does not claim CV recognition.

Provider label IDs, raw responses, bounding boxes, estimated nutrients, and provider-specific metadata are not part of this contract.

## 4. AnalysisResult

A completed backend result, returned to the mobile app and held in session memory.

| Field | Type | Meaning |
|---|---|---|
| `meal_id` | UUID string | Identifier of the meal being analyzed. |
| `computed_at` | UTC ISO 8601 string | Time the completed analysis was produced. |
| `iauc_mmol_l_min` | number | Backend-calculated iAUC in `(mmol/L)·min`. |
| `feedback` | object | Normalized, non-diagnostic dietary feedback. |

The `feedback` object contains:

| Field | Type | Meaning |
|---|---|---|
| `summary` | string | Brief explanation grounded in the submitted food information and calculated iAUC. |
| `suggestions` | array of strings | Dietary suggestions; may be empty. |
| `limitations` | array of strings | Relevant uncertainties or limits; may be empty. |

The backend calculates iAUC in the dedicated calculation module before calling the LLM. The LLM does not calculate or replace `iauc_mmol_l_min`.

Feedback must not contain medical diagnoses, medication recommendations, or insulin dosing.

The iAUC field defines a storage and transport unit only. Using minutes as the time unit does not define the monitoring duration.

BioSync v1 uses positive-only incremental area as defined in [IAUC_POLICY.md](IAUC_POLICY.md). Therefore, a valid BioSync v1 iAUC result is non-negative.


Window, baseline, interpolation, data-quality, and other calculation-policy rules are defined in `IAUC_POLICY.md`.

## 5. POST /v1/food-recognition (reserved; not implemented)

Original optional recognition design. No current Flask route implements it;
the following upload/response definitions are not available runtime behaviour.

### Request

Content type: `multipart/form-data`.

| Form field | Type | Required | Meaning |
|---|---|---|---|
| `meal_id` | UUID string | Yes | Identifier of the locally saved meal. |
| `image` | file, `image/jpeg` | Yes | Actual image file bytes. |

The mobile app saves the meal record and a persistent local image before making this request.

The endpoint does not accept `image_uri`, a local file path, or a remote image URL as a substitute for the file.

### Success response

HTTP `200 OK`.

| Field | Type | Meaning |
|---|---|---|
| `meal_id` | UUID string | Echoes the request's meal identifier. |
| `food_info` | `FoodInfo` | Normalized recognition result. |

The mobile app stores `food_info` against the corresponding meal and advances its local stage to `waiting_glucose`.

### Errors

The common errors apply.

Additionally, HTTP `422` with code `FOOD_NOT_RECOGNIZED` means the service completed but produced no usable food items. This does not establish a confidence threshold.

### Backend responsibility

The backend validates the upload, invokes the CV integration, normalizes its response, and returns the result.

No stored backend meal, image reference, or recognition session is required by the later analysis request.

## 6. POST /v1/analyses

Calculate iAUC and generate dietary feedback using the complete input supplied in this request.

### Request

Content type: `application/json`.

| Field | Type | Required | Meaning |
|---|---|---|---|
| `meal_id` | UUID string | Yes | Identifier of the current mobile draft, stable across unchanged retries. |
| `meal_at` | UTC ISO 8601 string | Yes | User-selected meal timestamp, serialized from the local Date. |
| `food_info` | `FoodInfo` | Yes | The normalized food information prepared by the mobile app. |
| `readings` | array of `GlucoseReading` | Yes | All readings required for this request under the confirmed calculation policy. |
| `other_meal_times` | array of UTC ISO 8601 strings | No | Timestamps of other logged meals, used only for policy-layer overlap detection. Defaults to an empty array. No backend meal storage is implied. |

The mobile app passes the selected provider's normalized readings from memory.
`readings` includes pre-meal baseline data and post-meal coverage. Current retrieval
is **[meal_at − 15 min, meal_at + 135 min)**; the analysis remains exactly 120 minutes.
The app sends `other_meal_times: []` because it has no reliable meal history.

A prior food-recognition call is not a backend prerequisite: this request is self-contained.

Clients do not submit a precomputed iAUC, a provider response, or an image URI.

### Success response

HTTP `200 OK`.

The response body is an `AnalysisResult`.

The mobile app validates the matching `meal_id`, sets the transient ViewModel
state to `success`, and displays iAUC and feedback. No persisted `completed`
MealRecord is created.

### Errors

The common errors apply.

The supplied readings must satisfy the scientific and data-quality requirements defined in [IAUC_POLICY.md](IAUC_POLICY.md). Calculation-policy failures are returned using the corresponding stable error codes.

Missing or unusable data must not be represented as a successful result with an invented zero iAUC.

The current form retains its input for retry but resets request results/status
when a new attempt or input change starts. There is no persistent result cache.

All six policy codes listed in IAUC_POLICY.md map to HTTP 422. Only
`WAITING_FOR_GLUCOSE_DATA` has `retryable: true`; the other policy errors require
input/data correction. Unexpected backend failures use HTTP 500 `INTERNAL_ERROR`
with a sanitized message and `retryable: false`. Strict schemas reject extra
request fields; client-supplied iAUC, image URIs and raw provider output are invalid.

### Backend responsibility

The backend:

1. Validates the request structure.
2. Applies the separately confirmed iAUC policy in the dedicated calculation module.
3. Sends normalized food information and the calculated iAUC to the LLM integration.
4. Normalizes the feedback and returns the completed result.

The backend does not wait through the monitoring period inside this request.

The specification requires calculation for up to 500 readings to complete within 500 ms, excluding network/API latency. This is a performance requirement, not a request-size limit defined by this document.




## 7. GET /health

Deployment liveness check, shared by local Flask and the Lambda adapter.
Returns HTTP `200` with `{"status": "ok"}`. It does not call OpenAI, calculate
iAUC, require an API key, or check provider readiness. No request body is required.

For API Gateway routing, packaging and manual deployment commands, see
[backend/deploy/README.md](../backend/deploy/README.md).

## iAUC Calculation Policy

Meal-specific scientific and data-quality rules are defined in
[IAUC_POLICY.md](IAUC_POLICY.md).

BioSync v1 currently uses:

- a 15-minute pre-meal baseline window;
- arithmetic mean baseline with at least two readings;
- a 120-minute postprandial window;
- positive-only incremental area;
- trapezoidal integration using actual timestamps;
- linear interpolation at the 120-minute boundary when required;
- no extrapolation;
- a maximum 15-minute adjacent data gap;
- explicit handling of duplicate/conflicting readings and overlapping meals.

These rules belong to the policy layer rather than the transport contract.
