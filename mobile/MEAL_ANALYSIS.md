# Manual meal + glucose provider analysis

Synchronized with code on **2026-10-11**. Current verification is listed in
[IMPLEMENTATION_STATUS.md](../docs/IMPLEMENTATION_STATUS.md).

The original fixture button and the local-only Health Connect diagnostic remain
available. The new form uses this path:

`HealthMealPanel → useHealthMealViewModel → selected GlucoseDataProvider → backendClient`
`→ API Gateway → Lambda → Flask → meal_analysis → iauc_service → mock or OpenAI feedback → mobile result`.

The current backend URL selects AWS HTTPS. Local Flask is an explicit alternative
configured in `src/config/development.ts`; it uses the same API and calculations.

Health Connect remains the default. The source buttons also select Samsung Health
without duplicating the request/analysis flow. Its setup, mapping and completed
physical-device verification are documented in [SAMSUNG_HEALTH.md](SAMSUNG_HEALTH.md).
The Health Connect procedure below remains applicable when that source is selected.

The checks below describe default mock mode. For real-provider setup and the
exact information sent to OpenAI, see [LLM_INTEGRATION.md](../docs/LLM_INTEGRATION.md).

No View calls native health APIs or fetch. Existing backend and Health Connect
mapping/service code are unchanged. No scientific calculation is done on mobile.

## Input and identity

- Enter one free-text meal description. Trim outer whitespace and create one
  `FoodInfo.items` entry with that `name`; do not add confidence or source fields.
  `FoodInfo` has no source property in the current contract.
- Optionally enter **Approximate weight (g)** for that single described dish.
  `350` becomes `weight_g: 350`, and decimals are supported. Blank/whitespace
  input omits the field entirely. Whole decimal/scientific numeric strings are
  accepted, but nonfinite values, zero, negative values, units such as `350g`,
  comma decimals and partial text are rejected before native access or HTTP.
  There is no added upper bound. Weight is user-supplied context only: it does
  not change glucose retrieval, baseline selection or iAUC. The application has
  no nutrient/calorie calculation or lookup; the LLM receives weight as context.
- `recognized_at` is the UTC time the user first confirms that manual draft by
  pressing Analyse. This task deliberately uses the transport field for manual
  confirmation; it is not a claim of backend/CV recognition.
- Meal time initializes as `selectedMealTime: Date = new Date()` when the
  ViewModel mounts. Separate native date/time pickers display the phone's local
  date and clock time. **Use current time** resets it. The normal form has no
  manual UTC text field. `@react-native-community/datetimepicker@9.2.1` supplies
  the Android picker; formatting is derived with `toLocaleDateString` and
  `toLocaleTimeString`.
- Submission derives `meal_at` with `selectedMealTime.toISOString()`. The existing
  UTC helpers and provider query interfaces are unchanged. Native/JavaScript
  handling uses the selected date's historical DST, not today's offset. For a
  Pacific/Auckland device, local 20 Sep 2026 17:13 corresponds to
  `2026-09-20T05:13:00.000Z`; local 4 Oct 2026 17:13 corresponds to
  `2026-10-04T04:13:00.000Z` (examples with seconds/milliseconds zero).
  No timezone selector or manual offset arithmetic is used. Samsung diagnostic
  start/end inputs still accept raw UTC ISO text; they are separate from this form.
- `meal_id` is a UUID v4 generated by the added, zero-dependency
  `react-native-uuid@2.0.4`. It is an association ID, not a security token.
- The current draft ID and `recognized_at` survive retries with unchanged meal
  time/text/weight/source. Changed normalized input or selected source creates a new
  ID at the next analysis.
  For example, `350` and `350.0` represent the same weight for retries; changing
  it to `400` or clearing it invalidates the previous result/draft at analysis.
  Draft state is in memory only; restarting the app resets it.
- Always send `other_meal_times: []`: there is no reliable meal-history source.
  Consequently the backend cannot detect an unreported overlapping meal here.

Manual weight example (the same `FoodInfo` works with the `weight_g` field omitted):

```json
{
  "recognized_at": "2026-10-04T02:00:00.000Z",
  "items": [{"name": "Chicken rice", "weight_g": 350}]
}
```

To verify the weight extension, enter a dish and `350`, submit with valid
Health Connect coverage, then retry without weight. Both requests remain valid
and the same glucose data must produce the same iAUC. Enter `0` or an invalid
value to see a local input error. Backend clients supplying invalid weights
receive HTTP 400 `INVALID_REQUEST`. Restart an already-running Flask process
after updating its schema; a non-reloading development server retains old code.

## Exact glucose query window

For meal time `t`, query **[t − 15 minutes, t + 135 minutes)**.
The start is inclusive and end exclusive, following Android's
[TimeRangeFilter.between semantics](https://developer.android.com/reference/androidx/health/connect/client/time/TimeRangeFilter).

The extra 15 minutes after +120 are retrieval support, not an extension of the
120-minute iAUC interval. They cover every potentially valid after-end neighbor
under the policy's maximum 15-minute real-source gap. An exact +120 record is
included. The service follows all pages and maps/sorts exactly as before.
Do not truncate the query at +120 or synthesize boundary points in TypeScript.

The entire provider-normalized `GlucoseReading[]` is forwarded unchanged. Samsung
mapping already flattens series, removes exact source repeats and rejects
conflicts; Health Connect mapping retains duplicates for the backend. The mobile form
does not select baseline samples, compute a mean, interpolate, discard duplicates,
enforce gaps or calculate area. The backend alone does that. Even an empty array
is submitted for the backend to report scientific insufficiency.

The query is bounded: readings at or beyond +135 are not requested. If the only
later record is outside this bound, it cannot provide a valid interpolation
bracket, and the submitted dataset can produce `WAITING_FOR_GLUCOSE_DATA` rather
than a gap diagnosis based on that excluded record. No successful iAUC is invented.

## Request and error handling

Only these fields are sent: `meal_id`, `meal_at`, `food_info`, `readings`,
`other_meal_times`. See the complete captured synthetic request at the end of
this document. Actual device IDs, dates and values replace the example data.

| Condition | UI representation |
|---|---|
| Invalid description/weight/time | `input` error; no native read or HTTP request |
| Permission denied, unavailable provider, native error | `health_connect` or `samsung_health` error/status; no HTTP request |
| Successful zero-record read | Count 0; submit `[]`; show backend policy result |
| `WAITING_FOR_GLUCOSE_DATA` | `waiting` state: more post-meal data is needed; sync and analyse again |
| `INSUFFICIENT_BASELINE_DATA` | `policy`: missing pre-meal readings |
| `INSUFFICIENT_GLUCOSE_DATA` | `policy`: inadequate coverage/gaps |
| `OVERLAPPING_MEAL` | `policy`: isolated analysis not possible |
| `CONFLICTING_GLUCOSE_READINGS` | `policy`: conflicting same-time readings |
| `INVALID_GLUCOSE_DATA` | `policy`: invalid glucose records |
| Connection failure/timeout | `network` error, separate from scientific conditions |
| Other server/protocol failures | `backend` error with the preserved code |
| Successful response, including iAUC 0 | Display the actual returned iAUC and feedback |

There is no timer, automatic resubmission, or invented zero result. Retrying
Analyse rereads the selected provider so newly synced readings can reach the backend.
Defaulting the meal to now does not bypass the backend's need for +120 coverage.

## Exact physical-device verification

1. Connect a USB-debugging-enabled phone with Health Connect and screen lock.
   Confirm it is the intended device using `adb devices -l`. Prepare a source
   app that writes BloodGlucose to Health Connect, or use Google's Health Connect
   Toolbox on a test device. Permission alone does not create glucose data.
2. Use the current AWS HTTPS URL, or explicitly configure local Flask as described
   in [README.md](README.md). For reproducible mock checks use a local backend
   with `BIOSYNC_LLM_MODE=mock` and a reachable LAN address for the phone.
   `http://10.0.2.2:5000` is an emulator-only local alternative, not the current default.
3. In `mobile/`, run `npm.cmd start`. In another terminal run
   `npm.cmd run android -- --no-packager`. Run `adb reverse tcp:8081 tcp:8081`
   if Metro needs forwarding. Reinstall the native APK to update its permission
   rationale. Only debug builds allow local cleartext HTTP.
4. Verify **Run Test Analysis** still returns iAUC **225**; feedback follows the
   backend's configured mode (deterministic mock or real OpenAI).
5. In the manual meal form, enter `Chicken rice with broccoli`. Choose a local
   meal date/time at least 135 minutes in the past, with data in the queried range.
   Verify the displayed UTC query corresponds to that local selection. Try
   **Use current time** and then reselect the historical meal before analysis.
   For a controlled test, use distinct blood glucose records at t−15 = 4 and
   t−5 = 6 mmol/L; then t+15, +30, +45, +60, +75, +90, +105 and +120 = 7 mmol/L.
   These must actually be written to the device's Health Connect datastore by
   the test/source app. Keep all records within its permitted history range.
6. Press **Request Meal Health Permission** and grant only blood glucose read.
   Check the rationale now explains that the Analyse action uploads selected
   data. Press **Analyse Health Connect Meal**.
7. Confirm `reading → submitting → success`, selected count 10 for the isolated
   dataset, and a Flask POST 200. The returned iAUC should be **225**, with the
   manual description mentioned in mock feedback. Current mock returns two
   suggestions; the UI also supports empty suggestions allowed by the contract.
8. Test end interpolation with another isolated test interval: replace its
   +120 record by +119 = 7 and +124 = 7, keeping the earlier post-meal readings.
   The query must retrieve +124 and the backend should still return 225. Mobile
   must not insert a synthetic +120 measurement.
9. Test waiting on an isolated interval with baseline data but no reading at
   or after +120. Expect `waiting`, code `WAITING_FOR_GLUCOSE_DATA`, and a message
   that more post-meal data is needed. Add/sync the missing records and retry.
10. On separate controlled intervals, test missing baseline records and a
    >15-minute post-meal gap with endpoint coverage. Expect the corresponding
    distinct policy errors. For a range with no records expect count 0 and
    `INSUFFICIENT_BASELINE_DATA`, not successful zero iAUC.
11. Revoke blood glucose access in Health Connect settings and press Analyse.
    Expect a permission/Health Connect error and no Flask POST. Restore access;
    when testing local Flask, stop it and retry. Expect a network error rather
    than a policy error. Stopping local Flask cannot interrupt the AWS endpoint.
12. Change the meal description/time and confirm old results clear. The local
    diagnostic and fixture paths must remain usable independently. Real data
    may not satisfy the backend policy; that is a reported condition, not a
    reason to fabricate data or relax policy.

## Scope and document differences

The lecturer/user-authorized manual food input is now reflected in PROJECT_SPEC.md.
The existing `recognized_at`
transport field is used as manual confirmation time instead of backend recognition
time. No source/confidence fields or API schema changes were introduced.
SQLite persistence remains deferred, so the earlier contract's persistence and
restart-recovery guarantees are not implemented here. Meal policy, numerical
service, glucose units and HTTP request/response schemas are unchanged. Local
HTTP remains debug-only. Real LLM access is backend-only and opt-in; no CV,
camera or charts are implemented. AWS deployment support and the HTTPS demo
configuration are present; the deployed version is not inferred from local code.
